## 📝 DESCRIPTION

The `livequiz-testmc-app-itn-02` App Service returned **HTTP 500 (Internal Server Error)** on every page that reads from Cosmos DB (e.g. `/admin`). The Cosmos account `livequiz-testmc-cdb-itn-01` is locked down to **private connectivity only** (public network access disabled, account keys disabled) by management-group governance, and is reachable exclusively through its private endpoint at `10.20.0.15` on the Testmc VNet.

The root cause was that the App Service had **no virtual-network integration at all**, so it had no network path to the private endpoint — the Cosmos FQDN resolved to the (disabled) public endpoint and every data call failed. The underlying blocker was that the App Service Plan was on the **Free (F1) tier**, which does not support regional VNet integration.

### Error Message

```
GET https://livequiz-testmc-app-itn-02.azurewebsites.net/admin
→ 500 Internal Server Error
"Internal Server Error"
```

(Underlying cause: the Cosmos SDK could not establish a connection to `livequiz-testmc-cdb-itn-01.documents.azure.com`, which — from outside the VNet — resolves to a public endpoint that is disabled.)

### Impact

- ❌ Every app route that reads/writes Cosmos DB failed with HTTP 500 (admin console unusable).
- ❌ The app was effectively down for its primary function (quiz data is stored in Cosmos).
- ✅ Static assets and non-data routes were unaffected (pure network/data-plane failure).

## 🔬 ANALYSIS

### Root Cause Analysis

#### Primary cause — the App Service had no network path to a private-only Cosmos DB

The Cosmos account is exposed **only** through a private endpoint (`10.20.0.15`) on `network-testmc-vnet-itn-01`, and its private DNS zone `privatelink.documents.azure.com` (linked to the VNet) already carried the correct A record `livequiz-testmc-cdb-itn-01 → 10.20.0.15`. However, the App Service was **not integrated into the VNet** (`virtualNetworkSubnetId = null`). Requests from the app therefore left over the public egress, where the Cosmos FQDN resolves to a **public endpoint that is administratively disabled** — so the connection could never complete, and the app surfaced the failure as a generic HTTP 500.

#### Why the app could not simply be integrated — the Free tier blocker

Regional VNet integration requires an App Service Plan on **Basic (B1) or higher**. The plan was on **F1 (Free)**, which does not offer VNet integration at all. This is why the "obvious" fix (add VNet integration) was not directly available and the plan had to be scaled first.

#### Why keys/public access could not be re-enabled instead

Management-group `modify` policies (the same governance documented for `samplestmcstitn01`) enforce `publicNetworkAccess=Disabled` and `disableLocalAuth=true` and re-apply them on every ARM write. Opening public access or using an account key is therefore not a viable path — **private endpoint + Entra ID RBAC is the only supported access model**.

#### Error manifestation

```
1. Browser → https://livequiz-testmc-app-itn-02.azurewebsites.net/admin
2. App handler calls Cosmos SDK against livequiz-testmc-cdb-itn-01.documents.azure.com
3. App is NOT on the VNet → DNS resolves to the PUBLIC Cosmos endpoint
4. Public endpoint is Disabled by governance → connection fails / times out
5. Unhandled data-layer error → ASP.NET returns HTTP 500 "Internal Server Error"
```

## ✅ SOLUTION IMPLEMENTED

### Fix Overview

Give the App Service a private network path to the Cosmos private endpoint by (1) scaling the plan to a tier that supports VNet integration, (2) creating a dedicated App Service integration subnet, (3) integrating the app and routing all outbound traffic through the VNet, and (4) confirming the Entra ID data-plane role. This mirrors the established `samples`/`aicm` pattern on the same VNet.

### Changes Applied

#### 1. Scale the App Service Plan F1 → B1 (Basic)
**Resource:** `livequiz-testmc-plan-linux-itn-01`

```powershell
az appservice plan update -n livequiz-testmc-plan-linux-itn-01 `
  -g livequiz-testmc-rg-itn-01 --sku B1
# Result: sku=B1, tier=Basic
```
Basic B1 is the minimum tier that supports regional VNet integration.

#### 2. Create a dedicated integration subnet (delegated to serverFarms)
**Resource:** VNet `network-testmc-vnet-itn-01`

```powershell
az network vnet subnet create -g network-testmc-rg-itn-01 `
  --vnet-name network-testmc-vnet-itn-01 `
  -n network-livequiz-testmc-snet-itn-01 `
  --address-prefixes 10.20.4.0/24 `
  --delegations Microsoft.Web/serverFarms
```
`10.20.4.0/24` was the next free `/24` (0–2 in use by PE/samples/aicm, 3 by the DNS resolver, 255 by the gateway).

#### 3. Integrate the app + route all outbound through the VNet
**Resource:** `livequiz-testmc-app-itn-02`

```powershell
az webapp vnet-integration add -n livequiz-testmc-app-itn-02 `
  -g livequiz-testmc-rg-itn-01 `
  --vnet network-testmc-vnet-itn-01 `
  --subnet network-livequiz-testmc-snet-itn-01

az webapp config set -n livequiz-testmc-app-itn-02 `
  -g livequiz-testmc-rg-itn-01 --vnet-route-all-enabled true
```
`vnetRouteAll` is required so DNS resolves through Azure DNS → the VNet-linked `privatelink.documents.azure.com` zone → `10.20.0.15`, and so Cosmos Direct-mode partition endpoints route through the VNet.

#### 4. Confirm Cosmos data-plane RBAC (already present)
**Resource:** `livequiz-testmc-cdb-itn-01`

```powershell
az cosmosdb sql role assignment list -a livequiz-testmc-cdb-itn-01 `
  -g livequiz-testmc-rg-itn-01
# Managed identity 03a27d59-... already holds role
#   00000000-0000-0000-0000-000000000002  (Cosmos DB Built-in Data Contributor)
```
No change needed — the role was already assigned to the app's managed identity.

#### 5. Restart and verify

```powershell
az webapp restart -n livequiz-testmc-app-itn-02 -g livequiz-testmc-rg-itn-01
# GET /admin → HTTP 200 (Admin Sign In page)
```

### Solution Features

#### ✅ Compliant private access
- Works **with** the governance model (private endpoint + Entra ID), not around it.
- No public exposure and no account keys.

#### ✅ Consistent with existing architecture
- Uses a per-app, serverFarms-delegated subnet (`network-livequiz-testmc-snet-itn-01`), matching the `samples` (`10.20.1.0/24`) and `aicm` (`10.20.2.0/24`) integration subnets.
- Reuses the already-linked private DNS zone and existing Cosmos private endpoint.

Any App Service that must reach a private endpoint requires **Basic B1 or higher**. Free/Shared tiers should not be used for apps consuming private-only Storage/Cosmos/SQL/Key Vault on this VNet.

## 🎓 LESSONS LEARNED

### What Went Wrong
1. **Wrong tier for a private-only dependency**: the app was deployed on Free (F1), which cannot integrate with the VNet needed to reach a private-only Cosmos DB.
2. **Missing network path masked as a generic 500**: the failure surfaced as a generic Internal Server Error rather than a clear networking/DNS error.

### What Went Right
1. **Governance guardrails held**: private-only + key-less enforcement pushed toward the correct, compliant fix.
2. **Reusable pattern existed**: the `samples`/`aicm` integration-subnet pattern, the linked private DNS zone, and the pre-existing Cosmos private endpoint and RBAC made the fix mechanical.

### Improvements for Future
1. **Provision apps at B1+ when they consume private endpoints** — treat Free/Shared as incompatible with private-only PaaS.
2. **Add a health/DNS probe** that fails fast (and clearly) when a private dependency is unreachable, instead of a generic 500.
3. **Codify the pattern** (dedicated serverFarms-delegated subnet + `vnetRouteAll` + Entra data role) as the standard onboarding checklist for this VNet.
